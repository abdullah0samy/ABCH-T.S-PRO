## 4. Architecture Review

The system is a fairly conventional, appropriately-sized NestJS + React + PostgreSQL (via Prisma) monolith — 13 backend modules (`auth`, `users`, `tickets`, `admin`, `analytics`, `assets`, `audit`, `jobs`, `knowledge`, `notifications`, `profile`, `team-notes`, `uploads`), ~19 frontend pages. This is **not** the sprawling multi-service "enterprise" system the brief's language implies — that's not a criticism, it's a scale calibration you should keep in mind when weighing "zero tolerance, thousands of users daily" against the actual size of the team maintaining ~30 backend files. The architecture is right-sized for what it is.

Migration approach: `main.ts`'s own comments say things like *"matching Express app.ts config exactly"* for Helmet/CORS/body-parser setup. That tells me the NestJS migration was a deliberate lift-and-shift of working Express middleware rather than a ground-up idiomatic NestJS rebuild. That's a legitimate, pragmatic choice — it minimizes behavioral drift during a migration — but it also means you're not yet getting some NestJS-native benefits (global `ValidationPipe` + DTO classes instead of ad hoc Zod parsing in two places, structured `@nestjs/config` schema validation instead of scattered `process.env.X || fallback` checks).

Validation strategy is split three ways: a `ZodValidationPipe` exists but is never applied via `@UsePipes`; a `tickets.schema.ts` Zod schema is applied *manually* inside the tickets controller/service (`.safeParse()` calls, not through the pipe); and every other endpoint appears to validate with hand-written `if` checks in the service layer. Pick one pattern and apply it consistently — right now there are three ways to validate a request in the same codebase, and none of them fully cover the other 53 endpoints the existing audit inventory counted.

`tickets.service.ts` is 1,007 lines and owns creation, listing, status transitions, assignment, transfer, archiving, bulk operations, and SLA math. That's a God Service candidate — not urgent, but worth splitting (e.g., `TicketWorkflowService`, `TicketQueryService`, `TicketBulkActionsService`) before it grows further, since every new ticket feature currently has to be threaded through this one file.

## 5. Backend Review (NestJS)

**Confirmed, build-breaking:** `backend/src/main.ts` does `import { doubleCsrf } from 'csrf-csrf'`; `backend/src/common/pipes/zod-validation.pipe.ts` and `backend/src/common/schemas/tickets.schema.ts` do `import { z } from 'zod'` / `import ... from 'zod'`. Neither `csrf-csrf` nor `zod` appears in `backend/package.json` dependencies, and neither appears anywhere in `backend/package-lock.json` (I grepped both directly — zero matches). `tickets.schema.ts` is not dead code; it's actively imported and used by `tickets.controller.ts`/`tickets.service.ts` for ticket creation and search. **Running `cd backend && npm ci && npm run build` (or starting the app) in a clean environment will fail on a missing-module error before the server ever boots.** This is priority zero — it's two lines in `package.json`.

**Confirmed dead weight:** `express-rate-limit` is a backend dependency with zero usages anywhere in `backend/src` (grepped, zero hits) — rate limiting is fully handled by `@nestjs/throttler` instead (confirmed wired up correctly via `@Throttle()` decorators on login/auth/search/analytics/upload routes). Harmless, but it's leftover weight from the Express era; remove it.

**Redundant fail-fast:** `auth.utils.ts` does its own `process.exit(1)` at module-load time if JWT secrets are missing, which fires *before* `main.ts`'s own explicit check ever runs (since `main.ts`'s static import of `AppModule` pulls in `auth.utils.ts` first). The end behavior (fail fast) is correct; the duplicate check in `main.ts` is effectively unreachable dead code. Minor, but confusing for the next person reading it.

**Inconsistent fail-fast posture:** JWT secrets correctly `process.exit(1)` if missing. `FRONTEND_URL`, used for both the CORS allowlist *and* the CSP `connectSrc` directive, falls back silently to `'https://yourdomain.com'` — a placeholder that will never resolve — if unset. If this env var is missing in a real deployment, the failure mode isn't a loud crash, it's a confusing, hard-to-diagnose CORS rejection of every legitimate request. Apply the same fail-fast pattern here that you already use for JWT secrets.

**Positive:** Swagger is correctly gated behind `NODE_ENV !== 'production'`. A `HealthController` exists for load-balancer checks. Named throttler buckets (global/login/auth/search/analytics/upload) are defined and, per spot-checks, actually applied via decorators rather than just declared and forgotten.

## 6. Database Review (Prisma / PostgreSQL)

**Genuinely good:** indexes are deliberately chosen and self-documented — `@@index([slaDeadline]) // SLA cron job scans every 5 min`, `@@index([departmentId, isArchived, status]) // Inbox compound filter pattern`. That's the kind of thing that usually only shows up after someone has actually watched slow query logs. Credit where due.

**Confirmed issue — two parallel role systems:** `User` has both a plain `role String @default("end_user")` field *and* a `roleId Int` foreign key into a full `Role` ↔ `Permission` many-to-many relational model. I grepped every service file for any read of `.permissions` off a `Role`, or any query against the `Permission` model — there are none. **The relational RBAC model is completely unused.** Every actual authorization check in the code reads the flat `role` string. This isn't catastrophic today (nothing is silently reading the wrong source), but it's a live foot-gun: whoever builds the next admin feature and sees a `Role`/`Permission` table will reasonably assume it's the enforcement mechanism, wire something against it, and get authorization decisions that quietly disagree with the guards everyone else's code respects. Either wire it in for real or remove it — don't leave two RBAC systems on the field with only one of them live.

**Confirmed issue — state fields aren't enums:** `status`, `priority`, `role`, `deptType`, `holdingStatus` are all plain Prisma `String`, not native `enum`. The only thing preventing `status: "asdlkfj"` from landing in the database is the application code checking against `TICKET_STATUSES`/`ALLOWED_TRANSITIONS` — there's no database-level constraint. Any future script, migration, admin tool, or direct DB access bypasses that entirely. Prisma enums are a small, low-risk change that would move this validation down to where it can't be accidentally skipped.

**Confirmed issue — JSON-as-string columns:** `Ticket.relatedTickets` and `UserPermissionOverride.allowedTransferDeptIds` are both stored as `String?` holding a JSON-encoded array, rather than either Prisma's native `Json` type or (better, for `relatedTickets` specifically) a real join table. You lose queryability ("show me every ticket related to #4471" requires pulling rows and parsing JSON in application code), referential integrity (nothing stops a related-ticket ID from pointing at a ticket that no longer exists), and indexing. This matches something the existing (otherwise questionable) `gap-analysis.md` also independently caught, and I confirmed it against the schema directly — one of the few things in the prior reports I can vouch for firsthand.

**Fine, once you check the defaults:** `checkTicketPermission`'s fallback logic (`userOverride?.[action] ?? dept?.defaultPermissions?.[action] ?? <hardcoded default>`) looks fail-open at first glance (`return true` when both are null), but `Department.defaultPermissionsId` is a *required* (non-nullable) relation, and every `DeptPermissions` boolean field has a concrete `@default(...)` — meaning that hardcoded final fallback is very likely unreachable dead code in a well-formed database. The actual default posture, driven by `DeptPermissions`'s column defaults, is sensible: routine actions (receive tickets, view dept tickets, assign, change status, transfer) default open; sensitive ones (export data, view analytics, view audit logs, manage dept users, manage KB, archive) default closed. Worth simplifying the code to remove the now-redundant fallback, but not a security bug.

**Small but real:** `invalidatePermissionCache()` is defined in `permissionCache.ts` and never called anywhere else in the codebase. The 30-second in-memory permission cache is invalidated only by passive TTL expiry — an admin revoking someone's `canArchiveTickets` override has no way to make that take effect immediately; it's a guaranteed-but-bounded 30 second wait. Cheap fix: call it from wherever `UserPermissionOverride`/`DeptPermissions` get written.

## 7. RBAC Review

RBAC here is genuinely two layers, and it's worth being precise about which layer does what, because the existing docs don't seem to distinguish them clearly:

1. **Coarse gate — `@Roles()` + `RolesGuard`.** Reads `request.user.role` (the flat string embedded in the JWT at login/refresh time) and checks membership in an allowed-roles list. This decides which *endpoints* you can hit at all.
2. **Fine-grained gate — `checkTicketPermission()` and equivalents in KB/analytics.** Merges department defaults with per-user overrides (with `super_admin` bypassing everything, and a hard rule that you can never act on a ticket outside your own department, transfer allowlist notwithstanding — see below) to decide which *specific actions* you can perform once inside an endpoint.

That's a reasonable, defense-in-depth design in principle. Two things to be aware of in practice:

- **Department isolation is absolute for status/assign/transfer/archive.** `checkTicketPermission` returns `false` immediately if `userDeptId !== ticketDeptId`, before any override is even consulted. Cross-department ticket handling appears to be governed separately, at the transfer-initiation step, by `DeptTransferAllowlist` — i.e., the allowlist controls which departments you're allowed to hand a ticket *to*, not whether you can act on a ticket that already belongs to someone else. If that's the intended model, it's sound; if anyone on the team expects the allowlist to grant direct cross-department action rights, that expectation is wrong given the current code, and worth a one-line doc clarification so nobody "fixes" this by accident later.
- **Role changes propagate on a delay, deactivation doesn't.** `JwtAuthGuard` does re-check `isActive`/`deletedAt` against the database on every request — so fully deactivating a user takes effect on their very next API call, which is good. But it does **not** re-check `role` or `departmentId` freshness; those are trusted straight from the JWT for the token's full 8-hour life (or until the next refresh, which does re-embed fresh values). For a hospital access-control system, that means a demotion (not a termination) has an up-to-8-hour propagation window. That may be an acceptable tradeoff, but it should be a decision your team makes on purpose, not a side effect nobody wrote down.

## 8. Security Review

Consolidating the security-relevant items from across the stack in one place:

| Item | Status | Detail |
|---|---|---|
| Refresh token exposure | 🟠 High | `auth.service.ts`/`auth.controller.ts` return `refreshToken` in the JSON response body *in addition to* setting it as an `httpOnly`, `secure`, `sameSite: strict` cookie. This defeats part of the point of `httpOnly`. Current frontend code (`Login.tsx` line ~40, `setAuth(data.user, data.accessToken)`) doesn't currently persist the body's refresh token anywhere I could find — so today's blast radius is smaller than it could be — but the backend shouldn't be handing it out twice regardless; any future "just grab it from the response for convenience" change would silently reopen this. Fix at the source: stop returning `refreshToken` in the body at all. |
| Access token storage | 🟠 High | `authStore.ts`: `localStorage.setItem('accessToken', accessToken)`. Any XSS anywhere on the page — now or in a future dependency — reads this directly, no `httpOnly` protection applies to `localStorage` at all. This is the textbook reason OWASP recommends against it. Given the CSP already restricts `scriptSrc` to `'self'`, moving the access token to an in-memory-only store (plus silent refresh via the httpOnly cookie, which the backend already supports and the frontend currently never calls — see Section 12) would close this without a large rewrite. |
| CSRF secret | 🟠 High | `getSecret: () => process.env.CSRF_SECRET \|\| crypto.randomBytes(32).toString('hex')` in `main.ts`. This isn't memoized — it's a fresh random value on every invocation if the env var isn't set. In a single-instance deployment this is already fragile; the moment you run more than one backend replica behind a load balancer (which "thousands of users daily" will require), each instance mints its own secret and CSRF validation breaks unpredictably across instances. Set `CSRF_SECRET` explicitly in every environment and consider removing the random fallback entirely so a missing env var fails loudly instead of "working" inconsistently. |
| CSRF token attachment | 🟢 Confirmed working | `apiFetch` reads the non-`httpOnly` `x-csrf-token` cookie and echoes it as a header on every request — correct double-submit-cookie implementation. (The CSRF cookie itself correctly is *not* `httpOnly`, by design — that's not a bug, that's how this pattern has to work.) |
| Session/token revocation | 🟠 High | No session or revoked-token table in the schema. "Logout" clears the refresh cookie client-side and does nothing server-side; an already-issued access token remains valid for its full lifetime regardless of logout. Combined with the localStorage exposure above, there's currently no way to force-kill a specific compromised session. |
| Frontend 401/403 handling | 🟠 High (business logic, cross-referenced from Section 12) | Any 401 or 403 triggers a full logout, everywhere. See Section 12.3 for the full explanation — it's really both a security-response-handling issue and a workflow bug. |
| SQL injection | 🟢 Low risk | Prisma parameterizes queries throughout; I found no raw SQL. The identifier-format regex check in `auth.service.ts` before lookup is reasonable defense-in-depth on top of that, not the only thing standing between you and injection. |
| Secrets in the current repo | 🟢 None found | No `.env`, no hardcoded credentials in any file I read. (This directly contradicts the existing `security-review-report.md`'s Finding 14 — see Section 2.) |
| CORS / CSP placeholder fallback | 🟡 Medium | Covered in Section 5 — same root cause as the CSRF secret issue: a missing env var degrades silently instead of failing loudly. |

## 9. Business Logic & Workflow Review

`workflow.constants.ts` is the standout artifact in this codebase and deserves to be called out specifically: the allowed-transition graph explicitly removes `resolved → closed` as a direct path, with an inline comment explaining *why* (enforcing "agent resolves → creator confirms → auto-close" as the intended hospital workflow, with a documented `super_admin`-only override for force-closing). That's exactly the kind of decision trail that makes a codebase maintainable by someone other than its original author — more of the codebase should read like this file.

Priority-based SLA modifiers are a clean multiplicative rule, easy to test, easy to reason about. The bulk-operation endpoints (`bulk-update-status`, `bulk-assign`, `bulk-archive`) correctly reuse the same `checkTicketPermission` gate per-ticket rather than checking once and assuming it applies to the whole batch — good, since department/override state could differ ticket-to-ticket even within one bulk call.

The one workflow gap worth flagging: the `closed → in_progress` (reopen) transition's comment says it's "super_admin only, enforced in route handler" — meaning the state-machine constants file only defines that the transition is *graph-legal*, and the actual role restriction lives elsewhere in the calling code, not here. I'd recommend a quick, explicit test asserting that a non-super_admin actually gets rejected on this specific path, since right now the constraint is documented in a comment rather than enforced in the same place the rest of the transition table lives — an easy thing to accidentally break in a future refactor without a test catching it.

## 10. Frontend Review

Component structure is conventional and readable — pages call `apiFetch` directly (87% of all network calls in the frontend go through it: 82 `apiFetch()` calls vs. 12 raw `fetch()`, which I counted directly rather than estimating). Zustand for global state (auth, notifications) is a reasonable, low-ceremony choice for this app's size — you don't need Redux here.

**Confirmed positive I want to flag on its own:** `NotificationProvider.tsx`'s Socket.IO setup already does the two things the "Stability Review" brief specifically worries about — it guards against duplicate connections (`if (socketRef.current?.connected) return;`) and explicitly tears down (`disconnect()`, `removeAllListeners()`) before establishing a new one, with bounded, backed-off reconnection attempts. This is already handled correctly; it doesn't need the fix the brief implies might be needed.

**Confirmed bug, connects two pieces of evidence:** that same socket connects via `io(window.location.origin, {...})` — hardcoded to the current page's own origin. The new `VITE_API_BASE`/`apiUrl()` mechanism (Section 3) was introduced specifically to support the frontend and backend living on different origins, and the new Dockerfile bakes `VITE_API_BASE` in at build time — but the socket setup was never updated to match. In any deployment where frontend and backend aren't on the same origin, real-time notifications and live ticket updates will silently fail to connect while regular API calls work fine, since only the latter got the fix. This is a one-line change (`io(API_BASE || window.location.origin, {...})`) but it's exactly the kind of thing that's invisible in dev (where everything's on `localhost`) and only bites in a real multi-origin production deploy.

**Setinterval usage (voice-note recording timers in `NewTicketPage.tsx`, `TicketDetailsPage.tsx`, `TeamFeedPage.tsx`):** these are UI-only timers (incrementing a recording-duration counter), not API polling, so they're lower-stakes than the brief's "polling without cleanup" framing implies. I confirmed `TicketDetailsPage.tsx` clears its interval correctly in the stop-handler; the other two follow an identical pattern so almost certainly do too, though I verified only the one directly. The remaining gap: these timers start on a button click, not inside a `useEffect`, so if a user starts recording and navigates away without clicking stop, there's no unmount-triggered cleanup to catch it. Low severity — worth a defensive `useEffect` cleanup, not an urgent fix.

`metadata.json` (new, at repo root) uses a `requestFramePermissions` field, which isn't a standard web-manifest key — it doesn't match typical PWA manifest schema (`name`/`icons`/`start_url`/`display`/etc.), and I found nothing in `index.html` or the Vite config that actually consumes this specific file. Worth a quick check that it's doing something real rather than being an orphaned artifact from whatever generated it.

### 12.3 Phase 4 — Security hardening: the specific bug, precisely

`api.ts` lines 38–49:

```
if ((response.status === 401 || response.status === 403) && !isLoggingOut) {
  ...
  logout();
  window.dispatchEvent(new CustomEvent('navigate', { detail: '/login' }));
  ...
  throw new Error('Session expired');
} else if (response.status === 401 || response.status === 403) {
  throw new Error('Session expired (logout in progress)');
}
```

Both branches treat 401 and 403 identically. But on the backend, `RolesGuard` and `checkTicketPermission` throw plain `ForbiddenException` (403) for completely mundane, expected "you don't have this specific permission" cases — e.g., a Supervisor without `canArchiveTickets` clicking Archive on a ticket. Under the current frontend code, that ordinary, expected denial **logs the user out of the entire application** and redirects them to `/login`, rather than showing an inline "you don't have permission to do this" message. This is a real, disruptive UX bug hiding inside what looks like security code, and it's a great example of how a backend design choice (uniform 403 for all permission failures) and a frontend design choice (uniform logout on 401/403) each look reasonable alone and produce a bug only in combination. Fix: only force-logout on 401; on 403, surface the error message and let the user continue their session.

Rest of the security checklist: RBAC-frontend/backend consistency — frontend doesn't currently duplicate any authorization logic that could drift from the backend (it just renders based on what the API returns), which is the right posture; XSS/storage — covered in Section 8; file upload validation — I did not deep-dive the upload module's file-type/size checks in this pass, flagging as unverified rather than asserting either way; path traversal — same, unverified, worth a dedicated look given `multer`/`sharp` are both in play for uploads.

### 12.4 Phase 5/6 — Performance & stability: what's actually checkable statically

- **Confirmed**: no request deduplication, no cancellation, no retry — consistent with 12.1.
- **Confirmed**: Socket.IO duplicate-connection guarding is already correct (Section 10) — this specific worry in the brief doesn't apply here.
- **Confirmed bug**: Socket.IO origin mismatch with the new `VITE_API_BASE` (Section 10).
- **Confirmed, low severity**: voice-recording timers lack unmount-safety cleanup (Section 10).
- **Potential N+1 pattern, moderate confidence**: bulk ticket operations (`bulk-update-status`/`bulk-assign`/`bulk-archive`) iterate tickets and call `checkTicketPermission` (and the underlying DB reads it triggers on a cache miss) per ticket inside the loop, rather than batching the permission resolution up front. With the 30-second cache warm, repeat calls for the same user/department are cheap; the first call in a batch for an uncached user/department pays a DB round trip per ticket. Not `UNKNOWN`, but also not independently load-tested — flagging as moderate confidence, worth a quick profile under a realistic bulk-action size (50–100 tickets) rather than assuming either way.
- Everything requiring an actual running system (P95 latency, DB query timing, memory under load, concurrent-user behavior) is **`UNKNOWN — runtime verification required`**, honestly, not estimated.

### 12.6 A tradeoff worth naming, not a defect

Serving the frontend via the `serve` npm package (new Dockerfile) instead of Nginx (removed `nginx.conf`) is a legitimate choice — simpler to configure, one less moving piece — but Nginx is generally the more battle-tested option for static-asset serving at "thousands of users daily" scale (more mature caching/compression/concurrency handling out of the box). Not urgent, just worth knowing you made a tradeoff here, possibly without meaning to frame it as one.
